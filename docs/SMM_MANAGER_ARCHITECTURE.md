# Архитектура SMM Course Manager

Статус: **версия `smm-courses-editor.user.js` v1.3.12 опубликована 25.11.2026; проверена логика распределения, требуется тестирование в реальных админках WordPress**.

### Что уже реализовано (v1.2.4)
- Единый устанавливаемый Tampermonkey userscript на пяти сайтах, `@updateURL` / `@downloadURL` с GitHub.
- Расширяемый реестр модулей и два пункта меню: «Редактор курсов» / «Редактор дат». В обоих модулях собственная вкладка «Как работать».
- Встроенная перетаскиваемая и изменяемая панель; полноэкранная панель в отдельной вкладке `/wp-admin/index.php?smm_manager=dashboard`.
- Задачи курсов и дат выполняются в отдельной рабочей вкладке. Состояние и команды синхронизируются через GM-хранилище. Для дат предусмотрен импорт старой очереди smmmaster.net.
- Редактор курсов сохранил оригинальный DOM-алгоритм и полную проверку до/после Update; это **1 рабочая вкладка** и последовательная обработка.
- Редактор дат сохранил WordPress Quick Edit, тест трёх ID, dry run, отчёты, паузу; ускоренный поиск через fetch с резервным переходом к обычному поиску.
- Настройка **1–5 параллельных GET-запросов поиска** в редакторе дат (включается вместе с ускоренным режимом). Изменения дат сохраняются **последовательно**, не в 5 параллельных POST.
- Защита от одновременного запуска редактора курсов и редактора дат на одном сайте, а также предупреждения о старом отдельном скрипте дат.

### Исправление редактора курсов в v1.3.7
- На вкладке **«Настройки»** добавлено **«Параллельных потоков» (1–5)**, по умолчанию 1.
- Одно нажатие «Начать» создаёт **не более N именованных рабочих вкладок**: `smm-manager-courses-<site>-w1` … `-w5`. Они повторно используются для всех следующих товаров через `location.assign()`, новый таб для каждого товара не открывается.
- При запуске очередь делится между независимыми хранилищами `bwo.wc.course.product.v1.<site>.worker.<id>`, поэтому сохранения разных воркеров не перезаписывают результаты друг друга.
- Dashboard собирает общие статусы 400 товаров из этих независимых состояний, показывая прогресс по каждому воркеру.
- Пауза/стоп передаются всем воркерам, в том числе ещё загружающимся. При ошибке с включённым `stopOnError` отправляется пауза соседним воркерам.
- Для прерванного `saving/verifying` статус переводится в **«Проверить»**, без автоматической повторной отправки Update. `opening/filling` возвращаются в очередь только после истечения блокировки и отсутствия подтверждённого сохранения.
- Синтетические проверки для 400 уникальных ID: 1 поток = 1 таб/400 курсов; 2 = 2×200; 3 = 134+133+133; 5 = 5×80. Проверены уникальность, сбор результатов и команды паузы. **Это не живой интеграционный тест WordPress.**

### Исправление видимости панели (v1.3.7)
- В v1.3.3 отсутствовал блок `const css`, из-за чего `mount()` завершался ошибкой `ReferenceError: css is not defined`; CSS восстановлен из v1.2.4.
- Убрана обязательная загрузка `@require` SheetJS на старте: библиотека Excel загружается только при импорте/экспорте. Недоступность CDN теперь не блокирует отображение панели.
- Добавлены резервная кнопка запуска и обработка сбоя инициализации, а также запуск без ответа устаревшего `GM_getTab` на обычных админ-страницах.
- Протестирован запуск в имитации DOM WordPress: панель смонтирована, редактор дат смонтирован, отображены оба модуля и три команды Tampermonkey, ошибок инициализации нет. Реальный браузер на пяти сайтах не проверялся.

### Восстановление очереди после нажатия Update (v1.3.12)
- После нажатия Update WordPress может полностью перезагрузить `post.php`, не сохранив callback `GM_getTab` или navigation ticket. В v1.3.12 установлен устойчивый идентификатор вкладки через `sessionStorage`; fallback загрузки теперь работает и в worker.
- Если билет потерян, worker с уже отправленным Update автоматически запускает **только GET/DOM-сверку с новой страницы**. Автоматическая повторная отправка POST/Update не выполняется.
- Дополнительная защита при смене адреса сайта между `www` и без `www`: при активном потоке разрешено восстановление worker по имени вкладки и идентификатору активной очереди; навигация нормализуется к текущему host.
- При ручном запуске после зависания `saving/verifying` с сохранёнными `expected` + `saveAt` переводится в `verifying`, а без данных для проверки — в `review`. Строки, которые ещё не дошли до Update, возвращаются в `pending`.
- Выполнена синтетическая проверка очереди из 443 разных ID: 1 строка -> verify-only; 1 неподтверждённая -> review; 441 осталась pending; потерь ID нет. Проверены условные ветки с валидным, отсутствующим и устаревшим билетом перехода. **Интеграционный тест с WordPress пока не проводился.**

### Исправление остановки на Update (v1.4.1)
- В v1.3.12 кнопка `#publish` нажималась через `button.click()`, а скрипт ожидал завершения нативной навигации WordPress. На части сайтов поток зависал на сообщении «Нажимаем Update».
- В v1.4.0 сохранение заменено на **один контролируемый POST** существующей формы `#post` через `fetch`, с `FormData(form, submitter)`. Перед POST обязательно проверяются `post_ID`, `action=editpost`, `_wpnonce`, тип/метод формы, адрес сайта и название. В журнал пишутся отправка, HTTP-код, redirect и конечный путь; nonce никогда не журналируется.
- **Не повторять POST** при тайм-ауте, 403/500, истечении сессии, ненормальном ответе или неподтверждённом результате. Отправленный товар переводится в `review`; ручная повторная отправка без проверки запрещена.
- При успешном HTTP-ответе скрипт открывает свежую страницу товара **в той же вкладке**; результат считается выполненным только после DOM-проверки всех требуемых полей. Изменения в WordPress могут не пройти сохранение, даже если HTTP=200.
- В v1.4.1 после подтверждённого POST снимается только стандартный WordPress `beforeunload.edit-post` обработчик, который иначе может блокировать программный переход. Таймер через 18 секунд диагностирует заблокированный переход и безопасно приостанавливает поток.
- Синтетически проверены: один POST при успехе; один POST без автоматического повтора при HTTP 500, login redirect и timeout; запрет POST при отсутствии nonce; перенос WordPress save submitter; watchdog при успешном и блокированном переходе. **На живом WordPress все ещё нужен тест 1 товара, затем двух потоков на небольшой очереди.**

### Не завершено / требует проверки
- Реальный smoke-тест WordPress/WooCommerce каждого из пяти сайтов: права, поля, поиск товара по ID, Quick Edit, ACF, медиатека.
- Тест ускоренного поиска дат на 3 ID перед включением на всей очереди; режим по умолчанию выключен.
- Пул **2–5 параллельных операций записи для разных товаров** добавлен в редактор курсов, но **не протестирован на живых магазинах**. Сначала проверить 2 потока на нескольких тестовых товарах и затем повышать до 3–5.
- Системное отключение загрузки изображений и других ресурсов при открытии полноценного DOM-редактора курсов не внедрено: риск нарушения TinyMCE/ACF/Media Library. Ускоренный поиск дат использует облегчённый HTML без изображений.
- Бенчмарк 50 товаров до/после, более строгие межмодульные блокировки по одному productId, расширенный мониторинг воркеров.

**Перед использованием:** остановить старые рабочие вкладки и выключить отдельный скрипт `smmmaster_random_dates.user.js`. Не запускать редакторы курсов и дат на одном сайте одновременно. Начинать с теста 1 курса и 3 дат; для параллельных курсов отдельно проверить 2–3 товара на 2 потоках.

Цель: объединить `smm-courses-editor.user.js` и `smmmaster_random_dates.user.js` в одну расширяемую систему Tampermonkey без сервера, FTP, WP-CLI и дополнительного WordPress-плагина.

## 1. Принципы
- **Один установленный userscript**: `smm-courses-editor.user.js`, `@name` «SMM Course Manager»; `@version` повышать при каждом выпуске. Сохранять `@updateURL` и `@downloadURL` на raw GitHub.
- Все пять доменов: smmmaster.net, hottestcourse.com, learnmarket.net, profcourse.com, bestsocials.online; HTTPS, c www и без.
- Два независимых функциональных модуля: `courses` и `dates`; возможность добавлять `ModuleRegistry.register(module)` без переписывания ядра.
- Каждому модулю выделить собственные настройки, очередь, историю, отчеты, вкладку «Как работать». Состояние разделять по каноническому домену и модулю.
- Не отправлять Update, пока не пройдены проверки данных/прав. При неопределенном результате POST не повторять автоматически, помечать «Проверить».

## 3. Интерфейс
Главное меню:
1. Редактор курсов → Импорт Excel / Очередь / Обработанные / Журнал / Настройки / Как работать.
2. Редактор дат → Импорт ID / Диапазон дат / Очередь / Обработанные / Журнал / Настройки / Как работать.
3. Общие настройки → сайт / параллельность / ограничения / положение панели / диагностика.

Два режима одной панели:
- **Встроенная**: draggable/resizable Shadow DOM поверх любой разрешенной страницы `/wp-admin/*`; запуск ручных операций.
- **Отдельная вкладка**: открыть с пользовательского клика `https://<host>/wp-admin/index.php?smm_manager=dashboard`; Tampermonkey рендерит полноэкранную панель поверх обычной админки. Вкладка не переходит между товарами и остается на месте; рабочие вкладки работают отдельно. Это все еще вкладка авторизованного WP-сайта, а не независимый внешний сервис.

Связь между контроллером и воркерами: `GM_getValue/GM_setValue`, `GM_addValueChangeListener`, дополнительно BroadcastChannel для обновлений в пределах origin, с commandId, revision и ACK. Контроллер показывает события из обоих модулей и не выполняет работу из-за своего обновления/перезагрузки.

## 4. Модуль «Редактор курсов»
Сохранить: XLSX/XLS/CSV, ID, Name, Description (HTML), Regular price, ACF lessons, img (14-значное имя файла), slug, Downloadable OFF, Image Media Library, проверку до Update и после сохранения, историю, статус «Проверить», отчеты, настройку паузы, тест одним товаром.
- Перенести существующий формат состояния `bwo.wc.course.product.v1.<site>` через контролируемую миграцию без потери очередей. До миграции автоматически сохранять JSON backup.
- Оптимизация: не открывать медиатеку, если нужная обложка уже установлена; по возможности искать attachment ID через аутентифицированный WordPress AJAX, а не полную модалку, с проверкой совпадения имени; сохранять DOM-режим как безопасный fallback.
- Устранить фиксированные sleeps там, где возможно наблюдать DOM/AJAX-событие; применить bounded timeout.
- При изменении Regular price отдельно проверить сохранение и очистку Sale price, если это соответствует заданной бизнес-логике.
- В DOM-режиме один worker = одна вкладка товара, без параллельных действий с одним товаром.

## 5. Модуль «Редактор дат»
Сохранить: импорт XLSX/XLS/CSV/TSV/TXT и ввод ID, уникализацию, выбор столбца, случайные даты внутри выбранного диапазона, исключение полуночи, dry-run, тест трех ID, паузу/продолжение, автопаузу при 5 отсутствующих ID, XLSX/CSV-отчеты и проверку результата.
- Даты, выбранные для конкретных ID, фиксировать в очереди **до отправки Update**: при возобновлении нельзя назначать другую дату уже отправленному ID без проверки.
- Мигрировать `smmmaster_dates_v1_state` из `localStorage` в единый хранилище только на smmmaster.net; исходные данные оставлять нетронутыми до успешной миграции.
- Основной кандидат на ускорение: вместо перехода по `edit.php?s=ID` для каждого товара использовать аутентифицированные `fetch`/WP `admin-ajax.php`, с корректными nonces и подтверждением `inline-save`. Сначала эксперимент с одним ID и сравнение сохраненной даты; если на сайте не работает — fallback на Quick Edit через DOM.
- Другие четыре сайта включать после проверки их WooCommerce/WP разметки и серверного поведения; не считать их совместимыми только по совпадению домена.

## 6. Производительность
| Режим | Потоки | Подход |
|---|---:|---|
| Safe | 1 | DOM-редактирование как сейчас, полная проверка |
| Balanced (после тестов) | 2 | Отдельные воркеры/табы или fetch/AJAX при подтвержденной совместимости |
| Fast (после тестов) | 3–5 | Пул задач, лимит запросов/сайт, задержка с адаптивным backoff |

- **Нельзя считать потоки Worker Threads**: Tampermonkey не дает самостоятельный многопоточный доступ к DOM WordPress. Параллелизм достигается несколькими вкладками или несколькими независимыми HTTP-запросами.
- Fetch HTML + DOMParser не загружает изображения/шрифты/видео как открытая страница; перед сохранением проверять наличие csrf/nonce и все поля. Не применять глобальный `window.stop()`/блокировку всех изображений: это может разрушить работу WP-медиатеки и редакторов.
- Для тяжелого редактора отказаться от обязательной загрузки модалки медиа, когда возможно использовать поиск attachment через AJAX. Не отключать нужный JavaScript/TinyMCE/ACF вслепую.
- Настройка concurrentWorkers (1..5), по умолчанию 1; повышать только после тестов каждого сайта. Ограничить количество запросов, 429/503 → пауза и backoff; не ретраить автоматически неподтвержденные сохранения.
- Замерять по каждому ID: время загрузки, открытия редактора, выбора изображения, сохранения, проверки, число сетевых ошибок. Сравнить 50 товаров до и после.

## 7. Защита от конфликтов
- Один координатор записи состояния на `<site>/<module>/<run>` с monotonic revision и ACK, heartbeat/lease для работников.
- Блокировка `<site>/<productId>` общая между `courses` и `dates`; оба модуля не могут менять один ID одновременно.
- Статусы: pending → leased → editing → saving → verifying → done / review / error. После crash в `saving` → review, не автоматический POST.
- Стоп/пауза — запрет на *следующий* товар, не отмена отправленного Update. После перезагрузки контроллера продолжают работать воркеры; после закрытия браузера нельзя гарантировать выполнение.
- Открытые старые userscripts отключить после перехода, иначе две программы могут обработать одну очередь.

## 8. Этапы внедрения и приемка
1. **Базовая ветка / резервные копии.** Тестовые 5–10 товаров и архив текущих очередей. Новое ядро без изменений бизнес-логики.
2. **Два модуля и единое меню.** Перенос date-логики; все нынешние операции выполняются в safe single-worker; вкладка «Как работать» по модулю.
3. **Dashboard в отдельной вкладке.** Встроенный/отдельный режим, синхронизация, команда Start/Pause/Stop, журнал; dashboard никогда не участвует в обработке.
4. **Оптимизация дат.** AJAX/fetch для поиска и сохранения, проверка и fallback; тесты на каждом домене.
5. **Оптимизация курсов.** Media Library API и другие узкие места, сверка HTML, цен, slug, ACF, обложек; fallback.
6. **Пул 2–5 воркеров.** Lease, блокировки, производительность, throttle, отказоустойчивость; сначала 2, затем 3–5.
7. **Релиз.** Повысить @version, обновить raw GitHub, smoke-тест пяти сайтов, инструкцию по отключению двух старых скриптов.

**Критерии приемки:** нет двойных Update; курс и дата не меняются одновременно для одного ID; возобновление после reload не теряет очередь; неоднозначное сохранение → review; отчеты сохраняют ID и исходные строки; на всех пяти сайтах проверены отдельные очереди; отдельная панель не навигирует вслед за рабочими вкладками; скорость подтверждена замерами, а не предположением.
